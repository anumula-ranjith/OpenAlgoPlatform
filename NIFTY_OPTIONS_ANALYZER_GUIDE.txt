STEP 1 - UNDERSTAND THE SIGNAL AND EXITS
Signals use NIFTY on NSE_INDEX, not the option's premium chart.
The script compares EMA 5 with EMA 20 on completed five-minute index candles.
It keeps EMA history across sessions and requires 21 completed candles.
On a fresh bullish crossover, it buys 65 units of the selected call in sandbox.
It exits that long position on the first of:
  - A fresh bearish crossover.
  - Option premium at/below 90% of the confirmed average entry price.
  - Option premium at/above 120% of that entry price.
  - 15:05 IST, or the normal end of the bounded rehearsal.
Entries are allowed from 09:30 until before 14:30 IST, one filled entry per day.
The script never shorts the call or adds to an existing position. The latest
already-completed candle is seeded at startup; it does not immediately trade an
old crossover. Signals older than six minutes, future signals and duplicates
cannot open a new position.

STEP 2 - UNDERSTAND THE EXECUTION BOUNDARY
Source: strategies/examples/nifty_25350ce_analyzer.py
Shared signal helpers: strategies/examples/first_nifty_strategy.py
Reads use the OpenAlgo SDK. Writes call only this checkout's sandbox service;
the strategy never invokes a live broker order endpoint. Every new submission
also verifies Analyze mode. It refuses expired contracts, changed lot sizes,
existing exposure/pending orders on this contract, and a second entry that day.
A file lock prevents two copies of this example from running simultaneously.
This version runs locally inside this OpenAlgo installation; it is not a
portable strategy client for a different remote OpenAlgo server.

Orders use marketable LIMIT prices approximately 0.1% from the observed option
premium, rounded to the verified tick. A submitted order is polled for up to ten
seconds. An unfilled order is cancelled; an uncertain outcome is not resent.
Successful placement is not treated as a fill: status and filled quantity must
confirm the entire 65-unit lot before the policy changes position state.

Stop and target are conditions monitored by the Python process, rather than
resting exchange or server-side protective orders. Prices can gap; the realized
simulated exit can differ from the threshold. Keep the application and process
running during a rehearsal. Do not use this learning example for live orders.
